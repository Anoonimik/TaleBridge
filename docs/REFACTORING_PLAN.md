# TaleBridge — план рефакторинга

Основание: [код-ревью от 5 ноября 2026](CODE_REVIEW_2026-11-05.md), `main@9f3b052`.

## Цель и порядок работ

Сделать совместную игру безопасной для данных GM и игроков, обеспечить достоверное сохранение, затем упростить развитие функций. Сохранить React, Zustand, существующие сценарии игры и поддержку Obsidian/TaleSpire. Изменять архитектуру небольшими проверяемыми PR; обновление фреймворков не выделять в самостоятельную цель без конкретного основания.

Зависимости этапов:

```text
0. Воспроизводимая база и регрессионные проверки
                  ↓
1. Серверная авторизация и разграничение данных
                  ↓
2. Безопасная запись и согласованный протокол
                  ↓
3. Устойчивая синхронизация и предметная модель
                  ↓
4. Архитектурные границы и адаптеры
                  ↓
5. Доступность, измерения, установка и выпуск
```

Исправления установщика, документации браузерного запуска и доступности можно готовить независимо, но выпуск версии с многопользовательской сетью должен дождаться этапов 1–3. Если потребуется быстрое промежуточное исправление безопасности, временно ограничить сервер loopback и отключить удаленный clipboard; явно обозначить, что LAN-подключения в такой версии недоступны.

## Этап 0. Зафиксировать воспроизводимую базу

Ориентир: 1–2 рабочих дня. Проблемы: R23–R25.

1. Зафиксировать baseline поведения на проверенном коммите, сохранить небольшие тестовые vault fixtures: два игрока, NPC, приватная сцена, публичный handout, неоднозначные имена, Unicode, CRLF, Markdown с несколькими действиями.
2. Добавить команды `typecheck`, `lint`, `test`, `build`; проверять plugin JS через ESLint/`checkJs` до его перевода на TypeScript. Включить правила React Hooks и неиспользуемых переменных. Не выполнять массовую косметическую переформатировку вместе с исправлениями.
3. Выбрать поддерживаемую LTS-версию Node, совместимую с текущим Vite, зафиксировать runtime и package manager. Добавить `engines`, документировать чистую установку через `npm ci`.
4. Добавить CI: чистая установка → typecheck → lint → содержательные тесты → production build. Windows job для установщика, если сохраняется Windows-специфичный способ установки.
5. Превратить диагностические сценарии `docs/audit/reproduce.cjs` в регрессионные тесты ожидаемого поведения по мере исправления. Сам диагностический файл не использовать как критерий «все исправлено»: сейчас успех означает воспроизведение дефектов.

Критерий завершения: новая чистая копия проекта воспроизводимо собирается; CI проверяет оба компонента; известные дефекты имеют fixtures и ожидаемый результат. Для приложения не требуется произвольный процент coverage — нужны проверки прав, записи и сетевого протокола.

## Этап 1. Закрыть доступ к данным и опасным операциям

Ориентир: 3–5 дней плюс проверка интеграции. Проблемы: R01–R04, R15–R16.

1. Описать модель доверия: хост GM, клиент GM в TaleSpire, игрок, владелец персонажа, опубликованный ресурс. LAN/VPN не считать подтверждением роли.
2. Добавить server-side сессии. Предусмотреть локальную процедуру подключения GM и приглашение/назначение игрока конкретному персонажу. Выбранный механизм должен работать в TaleSpire WebView и браузере. Не передавать GM PIN клиентам; ограничить подбор, срок и отзыв сессий.
3. Ввести централизованную проверку разрешений для каждой команды. Примеры: игрок читает/изменяет только своего персонажа и журнал; управление сценой/раздачей — GM; завершение своего хода — отдельная ограниченная команда, а не право заменить все состояние боя.
4. Разделить GM и player DTO. Удалить общий broadcast приватного `PLAYER_DATA`/журнала и скрытых сцен. Игрок получает только опубликованный read-aloud/handout и разрешенную проекцию боя.
5. Заменить `/vault-file?path=...` интерфейсом опубликованных ресурсов с ID. Проверять канонический путь, разрешенную область публикации, тип/размер и получателя; не возвращать arbitrary `TFile`.
6. По умолчанию удалить доступ клиента к clipboard хоста. Для сценариев, действительно требующих clipboard хоста, предусмотреть отдельную локальную capability с явным назначением доверенному клиенту. Сначала закрыть HTTP, затем исправлять устаревшие WebSocket-операции.
7. Заменить самописный WebSocket transport проверенной библиотекой, совместимой с Electron/Obsidian. Настроить payload/connection/rate limits, heartbeat, backpressure, проверку origin и безопасный error handling. CORS задавать по модели доступа; он не заменяет авторизацию.
8. Валидировать envelope и payload до выполнения команды: длины, enum, конечные числа, диапазоны HP/уровня, размер массивов. Ввести централизованный async dispatcher; ошибочный JSON и невалидный payload не должны создавать unhandled rejection.
9. Определить режимы транспорта: локальный HTTP/WS и защищенный сетевой HTTPS/WSS либо документированный защищенный proxy. Проверить совместимость с WebView; не усложнять локальный режим без необходимости.

Критерии приемки:

- Без сессии недоступны данные кампании, операции записи и clipboard.
- Игрок A не может читать или менять B даже при ручной отправке сообщения.
- При подключении игрок не получает PIN, скрытые сцены и GM-поля в сетевом payload.
- Прямой HTTP-запрос к приватному Markdown/неопубликованному файлу получает отказ.
- Неправильные origin, oversized frames и malformed payload завершаются контролируемым отказом; транспорт проходит целевые RFC-тесты.
- Тесты используют изолированный vault; реальные секреты и clipboard не нужны.

## Этап 2. Гарантировать сохранность документов и общий контракт

Ориентир: 3–5 дней. Проблемы: R06–R08, R10–R12, R16, R21.

1. Выделить `protocol`-модуль для клиента и плагина: discriminated union команд и событий, runtime-схемы, `protocolVersion`, `requestId`, `characterId`, результат выполнения и коды ошибок. Не смешивать версию протокола с версией компонента.
2. Согласовать названия команд атак, реализовать либо удалить неподдерживаемые маршруты. Добавить контрактную матрицу: отправитель → право → обработчик → ответ → получатель.
3. Ввести репозиторий заметок поверх Obsidian API. Использовать атомарное обновление и последовательную обработку изменений одного файла; там, где команда включает Markdown и frontmatter, отдельно определить транзакционную границу.
4. Заменять только управляемые Markdown-узлы/секции. Для начала достаточно точечных исправлений сохранения блоков и callback replacement; перевод всего Markdown на AST делать, если он действительно упрощает надежное сохранение формата.
5. Сохранять внешние абзацы, незнакомый YAML, порядок секций и пользовательские фрагменты. Добавить fixtures с `$&`, `$1`, кодовыми блоками, заголовками, двумя несмежными `dnd-action`, пустыми секциями и CRLF.
6. Возвращать ACK только после успешной записи, а не после приема команды. Добавить `revision` для обнаружения конкурирующих изменений и `requestId` для дедупликации повторов.
7. Исправить браузерную поставку: явно выбрать сервер статических файлов и отдавать по `/` frontend, а по `/health` статус. Не использовать Vite dev server как механизм production-поставки.
8. Исправить clipboard `data`/`payload` только в оставшемся разрешенном интерфейсе. Исполнитель TaleSpire должен быть известен серверу; игровые команды маршрутизируются адресно, а не всем подключенным экземплярам.

Критерии приемки:

- Параллельное изменение журнала и инвентаря не теряет ни одну правку.
- Обновление атак не удаляет никакой посторонний текст; literal `$` сохраняется буквально.
- Изменение атак проходит через UI/команду, сохраняется и остается после повторного чтения.
- Ошибка записи дает ошибку в UI; подтверждение появляется только после сохранения.
- Адрес из player guide действительно открывает приложение; health endpoint возвращает JSON отдельно.

## Этап 3. Привести синхронизацию к единой модели

Ориентир: 4–6 дней. Проблемы: R05, R08, R13–R14, R17–R20, R24.

1. Назначить стабильные ID кампании, персонажа, участника боя, сцены и опубликованного ресурса. Имя оставить отображаемым полем; не использовать неоднозначный substring-поиск для записи.
2. Сделать сервер источником истины для игрового состояния; задокументировать исключения для локальных настроек интерфейса. Добавить серверное хранение skills, temporary HP, заклинаний, ресурсов и иных игровых данных, которым нужна переносимость между устройствами.
3. Нормализовать клиентский state по ID. Проверять `characterId`/revision каждого ответа; выбранный персонаж не должен подменяться чужим update. Отделить выбор от объекта данных.
4. Ввести состояния сохранения: draft/local → pending → confirmed, отдельно error/conflict. Debounce привязать к ID персонажа; отменять или безопасно завершать его при смене экрана/персонажа. Сохранять локальный черновик перед возможной потерей сети.
5. При reconnect сначала согласовывать snapshot/revision, затем повторять только допустимые идемпотентные команды. Определить разрешение конфликтов, а не молча применять последнюю доставку. Очередь должна иметь размер и срок хранения.
6. Разорвать связь «сокет существует = соединение актуально»: generation/instance guard, отмена старых listeners/timers, backoff с jitter, явный `connect/disconnect/dispose`.
7. Вынести endpoint configuration с host/port/scheme и единым построением HTTP/WS/media URL. Проверить реальный другой компьютер и нестандартный порт.
8. Объединить операции изменения HP между листом и боем либо явно определить их проекции. Активный ход хранить ID; порядок и переходы изменять атомарно.
9. Связать броски с запросом и действием. Инициатива должна использовать итог соответствующего броска; посторонний результат не завершает death save. Корректно обрабатывать таймаут и отсутствие TaleSpire. Секретные результаты доставлять только разрешенным клиентам.
10. Определить грамматику dice expressions и не обрезать сложные формулы. Для неподдерживаемой формулы показывать ошибку до выполнения.
11. Хранить active scene ID, вычислять актуальный объект; при удалении выбранной сцены явно выбирать следующую и чистить невалидную историю.
12. Добавить versioned storage namespace: campaign ID + character ID + schema version. Миграция старых данных должна сохранять копию, различать неоднозначные имена и не затирать подтвержденное серверное состояние.

Критерии приемки:

- Два клиента с разными персонажами не подменяют данные друг друга.
- Потеря сети, повторная доставка, ответы в другом порядке и reconnect сохраняют правильный итог.
- Навыки, temp HP и предусмотренные серверной моделью ресурсы переживают refresh и смену устройства.
- На другом хосте и нестандартном порту загружаются медиа.
- Удаление/пересортировка предыдущего участника не меняет активный ход; случайный чужой бросок не влияет на death save.
- Обновленная сцена сразу видна при сохраненном выборе.

## Этап 4. Упростить архитектуру без переписывания продукта

Ориентир: 3–5 дней после стабилизации контрактов. Проблемы: R23 и сопровождение ранее исправленных модулей.

Целевые направления зависимостей:

```text
React UI → use cases → domain
               ↓ ports
         transport / vault / TaleSpire adapters

app composition root связывает use cases, adapters и store
protocol schemas используются на обеих сторонах соединения
```

Предлагаемая структура, которую можно вводить постепенно:

```text
packages/protocol/           # wire-типы, схемы, ошибки, совместимость
packages/domain/             # персонаж, бой, броски, стабильные идентификаторы
obsidian-plugin/src/
  plugin.ts                  # lifecycle Obsidian
  server/                    # HTTP, WebSocket, session/auth, dispatcher
  application/               # обработчики команд, права и use cases
  vault/                     # поиск, parsing, безопасная запись, индекс
symbiote/src/
  app/                       # composition root, страницы, запуск адаптеров
  entities/*/model/           # предметный state и selectors
  features/*/model/           # операции пользователя
  shared/api/                # транспорт без знания React store
  shared/ui/                 # доступные базовые компоненты
```

Не обязательно сразу вводить полноценный monorepo tooling: сначала общий пакет контракта и управляемая сборка плагина. Итоговый `main.js` остается артефактом, который Obsidian может загрузить.

Работы:

1. Убрать импорт store из транспортов; транспорт публикует типизированные события и выполняет запросы. Composition root подключает подписчиков.
2. Убрать подключения из module constructors. Инициализацию выполнять явно с cleanup, пригодным для тестов и React StrictMode.
3. Разделить `useRosterStore` по предметным задачам; повторяемую логику хранения вынести в адаптер persistence. Доменные вычисления оставить чистыми функциями.
4. Перевести plugin source на TypeScript и собирать единый совместимый `main.js`; Electron/Obsidian оставить external.
5. Типизировать только используемую поверхность TaleSpire API, проверять входные события. Неподтвержденные API-вызовы закрепить интеграционными fixtures/контрактами по официальной документации.
6. Ограничить barrel exports и циклы через lint/анализ import graph; правило должно предотвращать обратные зависимости transport → store.
7. Перейти на Zustand selectors там, где компоненты подписаны на большие store. Профилировать до и после; не добавлять `memo`/`useMemo` повсеместно.
8. Убрать названия конкретной кампании и имена персонажей из общих парсеров в настройки/явные frontmatter-поля.

Критерий завершения: транспорт и domain тестируются без браузера/Obsidian; плагин проверяется TypeScript; описанных циклов нет; интерфейс сохраняет существующие игровые сценарии.

## Этап 5. Доступность, производительность и надежный выпуск

Ориентир: 3–5 дней и реальная игровая проверка. Проблемы: R09, R21–R25.

1. Сделать общий доступный dialog: имя, dialog semantics, начальный и возвращаемый фокус, Tab/Shift+Tab, Escape, блокировка фона, корректная работа вложенных окон. Проверить реальную поддержку выбранной реализации в WebView.
2. Связать labels и inputs, добавить имена icon-only controls, `aria-expanded`/`aria-controls` для аккордеонов, видимый фокус и объявления статуса сохранения. Автопроверки дополнить ручной клавиатурой и screen reader.
3. Проверить весь основной пользовательский путь на 375/768/1440, масштабе 200%, длинных русских строках и on-screen keyboard. Измерить контраст, не делать вывод по визуальному впечатлению.
4. Замерить startup/interaction в TaleSpire WebView и браузере; только затем согласовать budgets. Разделить GM/player/heavy modal chunks через lazy loading, если это улучшает замеры.
5. Измерить сканирование vault на небольшом и большом наборе заметок; убрать повторные полные scans на handshake, индексировать изменения, учитывать rename/delete и обновления metadata cache.
6. Исправить установщик: проверка допустимых абсолютных целей, корректная обработка Junction, backup `data.json`, staging и откат, рабочий `CopyMode`, явные ошибки. Копировать только runtime-артефакты, исключая `node_modules` и аудит.
7. Согласовать лицензию с владельцем проекта; синхронизировать metadata и версии компонентов/протокола. Обновить инструкции Node, браузерной поставки и сети под фактический результат.
8. Выпускать проверяемый release artifact. Если `dist` остается в Git, CI должен контролировать соответствие исходникам; если выпускается архивом — проверять установку архива в чистой среде.
9. Логи сделать структурированными по `requestId`/типу события; не логировать секреты, содержимое личного журнала и clipboard. Добавить диагностику подключений и ошибок записи без раскрытия игровых данных.

Критерии приемки:

- Основные сценарии проходят клавиатурой; screen reader правильно определяет диалоги и поля.
- Переустановка в copy и junction режимах не теряет настройки; неудача установки оставляет работоспособную предыдущую версию.
- Release ставится по README без ручных исправлений; версия и лицензия согласованы.
- В реальной игре проверены два игрока, GM, приватность заметок, камера, открытые/секретные броски, media, HP, атаки, reconnect и одновременное редактирование.

## Оценка и контроль риска

Грубый ориентир для одного разработчика, знакомого с проектом: **20–30 рабочих дней**, плюс время на проверку в реальных Obsidian/TaleSpire и принятие продуктовых решений. Это оценка объема, не обещание срока; основной разброс связан с механизмом подключения WebView, миграцией игровых данных и совместимостью API.

До миграций сделать резервные копии документов и локальных данных. Миграции должны быть версионируемыми и повторяемыми; не изменять неизвестные пользовательские поля. Для несовместимого протокола выводить понятное требование обновления, а не продолжать молча. Не пытаться обеспечить откат нового состояния старым клиентом без явно определенной совместимости.

Завершенность определять по проверяемым условиям этапов и реальной сессии, а не по числу новых файлов, размеру diff или проценту покрытия.
